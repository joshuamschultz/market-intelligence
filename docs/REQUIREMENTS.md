# Requirements checklist

Source: `PRD.md` v1.0 (November 21, 2026), plus the user's delivery instructions to keep a usable preview running, refresh application versions every 15–30 minutes, and load actual EODHD provider data into the database. This checklist separates implemented software workflows from provider-data completeness. `[x]` means the software capability is implemented and supported by current evidence; it does not certify every symbol/date/data field. `[ ]` means the full stated requirement remains open. Data limitations are called out inline and in the status table.

## Product scope and priorities

- [x] Provide a US equity research and decision-support platform for stock leadership, industry/sector/theme strength, and constituent-level market health. It is presented as research, not automated trading.
- [ ] Preserve a complete, historically accurate universe across the full provider dataset. The software shares versioned analytical context, computes numerator/denominator breadth, and exposes coverage, but current identity/type history is incomplete.
- [x] Implement the core P0 routes: Market Overview, Stock Screener, RS Rankings/Engine, Stock Detail, Industries, Historical Explorer, and separate Market Monitor.
- [x] Implement the primary saved-work flows: reusable screens, watchlists, cohorts, and in-app alerts. Some dynamic alert and universe/data coverage requirements remain open below.
- [x] Implement research UI and API workflows for cohorts, event studies, and factor backtests. Their available sample and point-in-time inputs remain data-limited.
- [x] Provide navigation for Market Overview, Stock Screener, RS Rankings, Industries, Historical Explorer, Saved Screens, Alerts, Settings & Data, and Market Journal.
- [x] Keep a usable preview running, refresh the browser build without clearing SQLite, and retain the loaded data across app refresh. The managed preview and HTTP/browser access were verified; app assets prompt for reload when a newer build is available.

## Conflicts, feasibility limits, and decisions to track

- **PRD scope vs. build window:** P0 alone spans broad historical data, many analytics, full screener and historical explorer, monitor, and group intelligence. The PRD's 12-week roadmap is an estimate, while the user's preview cadence adds a continuous delivery requirement. Implement a truthful, useful vertical slice and label unimplemented areas; do not represent the whole PRD as done.
- **Provider evidence required:** The user requires real EODHD data in the database, while the PRD explicitly says not to assume provider coverage. Actual availability/licensing for 10+ years across the full universe, delisted/ticker history, historical float and point-in-time classifications needs evidence. Clearly show populated date range, coverage, missing fields, and ingestion status; do not infer unsupported history.
- **Stack decision/tradeoff:** The team selected a Node modular monolith with durable SQLite for an immediately usable local preview. This differs from the PRD's recommended Next.js/FastAPI/PostgreSQL/DuckDB/Polars/Parquet stack; §15.1 is guidance, not a mandate, so this is a deliberate implementation choice rather than a violated requirement. Preserve the canonical calculation engine, point-in-time schema, provenance, and reproducibility; assess SQLite and local-file performance against the stated scale targets before claiming them met.
- **Fresh app vs durable data:** 15–30-minute app refreshes must not reset/delete loaded provider data. Separate frontend/app deployments from database/backfill lifecycle and verify persistence after a refresh.
- **Unfinalized defaults:** Section 23 labels defaults proposed pending technical design. Make each configurable or explicitly decide and record it, particularly universe eligibility, history sufficiency/denominators, dividend treatment, industry scoring, thresholds, and health calibration.
- **Data gaps:** Historical float and dated classification are acknowledged as hard/possibly unavailable cheaply. Missing values must remain missing and calculations depending on them must expose limited coverage rather than fabricate history.
- **Examples are not specifications:** Dashboard sample counts/scores are illustrative, and Stockbee-specific formulas must not be claimed without verification.
- **Scope status:** core P0 interfaces and several P1/P2 workflows are implemented and marked above. Full PRD completion still depends on unfinished data-quality, advanced analytics, recovery, and deployment requirements; do not infer full scope completion from a completed route.
